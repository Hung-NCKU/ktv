# KTV 雙軌錄音機

同時錄下**你的麥克風**和**這台電腦正在播放的聲音**，各存一軌，再自動對齊混成一個檔案。
不需要安裝虛擬音效線（VB-Cable / 立體聲混音），用的是 Windows 內建的 WASAPI loopback。

> **想了解背後的原理與踩過的坑？** 請讀 [docs/TUTORIAL.md](docs/TUTORIAL.md) ——
> 一份教學／研究用文件，記錄了六個真實遇到的作業系統層面問題，
> 每一個都附上量測數據與可重現的腳本。

## 快速開始

需求：Windows 10/11、Python 3.10 以上。

```bat
git clone https://github.com/Hung-NCKU/ktv.git
cd ktv
setup.bat
```

`setup.bat` 會建立 `.venv`、安裝套件、列出偵測到的音訊裝置。之後就用下面的檔案：

| 檔案 | 用途 |
| --- | --- |
| `錄音.bat` | 開啟圖形介面（建議） |
| `錄音-命令列.bat` | 命令列版，可加參數 |
| `setup.bat` | 重建虛擬環境（換電腦或環境壞掉時才需要） |

按 **F9** 或按鈕開始／停止錄音。停下來之後會進入試聽，**確認滿意再按「確定存檔」**。

## 試聽與存檔

錄音停止後不會自動存檔，而是先讓你聽過：

- 波形上**點一下或拖曳**就能移動播放位置，播放頭會跟著跑。
- **空白鍵**播放／暫停。
- 「**麥克風時間微調**」補償硬體延遲造成的人聲落後，見下一節。
- 試聽中拉動增益滑桿會**即時重新混音**（約 2 ms），可以邊聽邊調人聲和伴奏的比例。
- 滿意就按「**✓ 確定存檔**」，不滿意按「**✗ 捨棄**」，什麼都不會留下。

還沒存檔前，分軌其實已經寫在 `recordings\.pending_<時間戳>\` 暫存目錄裡 —— 不把整首歌
扛在記憶體（五分鐘雙軌要 200 MB 以上），程式當掉素材也還在。按下存檔才把混音寫出來、
分軌搬進正式資料夾；捨棄就整個刪掉。

如果程式沒正常收尾，下次開啟時狀態欄會告訴你有幾個 `.pending_` 暫存目錄留著，
裡面的分軌可以直接拿去用。

## 輸出

按下「確定存檔」後，會在 `recordings\<日期時間>\` 建一個資料夾：

```
recordings/20260919_213045/
  mic.wav                      麥克風原始軌（無增益、無處理）
  system.wav                   系統播放原始軌
  20260919_213045_mix.wav      對齊並套用增益後的混音
```

混音格式可選 `wav` / `mp3` / `m4a` / `flac`，轉檔用的 ffmpeg 已經附在 `.venv` 裡。
不想留分軌可以取消「保留分軌」，但建議留著 — 事後想重新平衡音量時會用到。

## 裝置選單

介面上方兩個下拉選單：

- **輸入（麥克風）** — 你要錄的收音裝置。
- **輸出（要錄的播放裝置）** — 錄的是「這台電腦透過這個裝置正在播放的聲音」。
  選你實際在聽的那個喇叭或耳機，選錯了會錄到一片安靜。

任一邊都可以選「不錄」，變成單軌錄音。換裝置後按「重新掃描」。
選好的裝置、增益、格式會記在 `config.json`，下次自動帶入。

## 增益

兩條滑桿（−24 ~ +12 dB）**只套用在最後的混音檔**，分軌原始檔永遠是原音。
錄完覺得比例不對，改滑桿重錄不划算 — 直接拿分軌用任何音訊軟體重混即可。

勾「混音爆音時自動降增益」的話，兩軌相加超過 0 dBFS 時會整體等比降下來，不會削波失真。

## 麥克風時間微調（延遲補償）

人聲在混音裡聽起來比伴奏晚，是**硬體延遲**造成的，不是錄壞了：

- Loopback 抓到的是「即將送去喇叭」的訊號，你真正聽到它還要再經過輸出裝置的延遲。
- 你跟著唱的聲音，也要經過麥克風的擷取延遲才進到程式。

兩段延遲相加，人聲就會落在伴奏後面。程式原本只用「資料抵達的時刻」對齊，補不了這段。

試聽區的「**麥克風時間微調**」就是補這個用的，範圍 ±500 ms，**負值把人聲往前拉**。
可以拉滑桿，也可以直接在旁邊的欄位打數字（已知數值時打字比拉精準）。改動會即時
重新混音，邊聽邊調。

**延遲主要由輸出裝置決定，所以這個值依輸出裝置分別記住。** 換裝置時會自動載入該
裝置的設定；沒記錄過的裝置一律從 0 開始（不沿用上一個裝置的值 —— 那幾乎肯定是錯的）。

這台機器的實測值：

| 輸出裝置 | 需要的微調 |
| --- | --- |
| ASUS VG328（螢幕喇叭，NVIDIA HDMI） | −64 ms |
| ROG DELTA S WIRELESS（無線耳機） | 約 −300 ms（量測不精確，無線延遲本來就大） |

`ASUS VG328` 的 −64 ms 已經預先填在 `config.json` 裡。無線耳機請自己調 —— 無線
傳輸的延遲差異大，而且戴在頭上麥克風收不到它的聲音，沒辦法用儀器量。

### 自己量的方法（需要喇叭外放）

麥克風聽得到喇叭時，可以用聲音本身校準：

1. 播一段有明顯節奏點的音樂，**開喇叭外放**，錄 10 秒。
2. 試聽時把「保留分軌」打開，錄完拿 `mic.wav` 和 `system.wav` 去音訊軟體對比同一個
   鼓點的位置差 —— 那就是要填的值（取負號）。
3. 或者直接用耳朵：拉滑桿到人聲和伴奏聽起來「合」為止。

戴耳機錄的話沒辦法這樣量，只能靠耳朵調。

## 掉樣本與時脈飄移

錄音最怕的不是雜訊，是**掉樣本** — WASAPI 的擷取緩衝區來不及被讀走就會覆寫，
那段聲音就永遠不見了，兩軌還會從此錯開。

程式用兩個設計避免這件事：

- **WASAPI 緩衝區開到 1 秒**（`buffer_frames`）。soundcard 的 `blocksize` 參數直接
  決定緩衝區長度，它預設只有 1024 frames ≈ 21 ms，任何一次排程停頓或 GC 都會溢位。
- **寫檔交給獨立執行緒**。擷取迴圈只把資料丟進佇列，磁碟卡頓不會連累擷取。

實測（這台機器，60 秒雙軌錄音）：

| 設定 | 掉資料次數 | 麥克風偏差 | 系統音偏差 |
| --- | --- | --- | --- |
| 21 ms 緩衝、寫檔在擷取迴圈裡 | 9 | −41.5 ms | −46.8 ms |
| 1 秒緩衝、獨立寫檔執行緒 | 0 | −0.2 ms | +1.8 ms |

修好之後可以看清楚：**兩個裝置的時脈其實都穩在 48000 Hz，差距在 0.003% 以內**，
一首四分鐘的歌累積誤差約 8 ms，聽不出來。（先前以為有 0.1% 時脈差，那是緩衝區
溢位污染出來的假象。）

程式仍然保留飄移修正 — 記下每軌串流的實際起訖時刻，用「牆鐘時間 vs 取樣數」回推
真實取樣率，重新取樣回 48 kHz 後依起始時間對齊。但它只在可信的條件下才動手：

- 錄音短於 15 秒不修。那種長度下起停時刻的量測誤差比真實飄移還大。
- 推算出的飄移超過 0.5% 不修。那代表量測出錯，不是硬體真的差這麼多。
- **該軌掉過資料就不修。** 少掉的取樣數是真的不見的時間，不是時脈跑得慢；
  拉伸整軌等於把一個局部斷點抹散到整首歌，只會更糟。

狀態欄會印出每軌的起始偏移、飄移量、是否修正，以及掉資料次數。
**如果看到「掉資料 N 次」，那次錄音的同步就不可靠**，建議關掉背景吃 CPU 的程式重錄。

## 命令列用法

```bat
.venv\Scripts\python -m ktvrec.cli --list                        列出所有裝置編號
.venv\Scripts\python -m ktvrec.cli                               互動選單
.venv\Scripts\python -m ktvrec.cli --mic 2 --sys 2 --duration 240 --format mp3 --yes
.venv\Scripts\python -m ktvrec.cli --mic 2 --sys 2 --mic-gain -3 --mic-offset -64
```

沒給 `--duration` 就是按 Enter 停止，錄音中會顯示即時音量條。錄完會印出這次的品質
資訊並問「要存檔嗎？」，回答 `n` 就整個丟掉。寫在腳本裡請加 `--yes` 直接存檔。
命令列版沒有試聽功能 —— 要聽過再決定請用圖形介面。

## 關於 WSL

**錄音本身不能跑在 WSL 裡。** WSL2 是虛擬機，沒有 Windows 音效裝置的直通權限：
它看不到你的麥克風，也拿不到 WASAPI loopback。網路上用 PulseAudio 橋接的做法只能
把聲音「播出去」，不能穩定地「錄進來」，而且延遲與掉包會讓雙軌對齊失去意義。

所以擷取這段必須留在 Windows 原生執行。後製轉檔倒是無所謂跑在哪 — 這裡選擇把
ffmpeg 直接裝進 `.venv`（`imageio-ffmpeg` 套件），不需要 sudo，也不用管 WSL 的檔案
系統跨界效能問題。

## 疑難排解

**系統那軌全是靜音** — 輸出裝置選錯了。Windows 是「每個輸出裝置各有各的 loopback」，
要選你聲音實際送去的那一個。在工作列音量圖示上確認目前的播放裝置。

**開始錄音失敗，說裝置被佔用** — 某些獨佔模式（exclusive mode）的程式會鎖住裝置。
到「音效設定 → 該裝置 → 進階」關掉「允許應用程式獨佔控制此裝置」。

**麥克風有回音** — 喇叭外放時，麥克風會收到伴奏，混音後伴奏就出現兩次。戴耳機錄。

**狀態欄出現「掉資料 N 次」** — 系統忙不過來。關掉背景的瀏覽器分頁、遊戲、防毒掃描
再錄。若持續發生，把 `config.json` 的 `buffer_frames` 加大（48000 = 1 秒，可試 96000）。

**藍牙耳機的麥克風音質很差** — 藍牙一旦啟用麥克風就會切到 HFP/HSP 模式，音質
大幅下降，連帶把播放音質也拉低。建議用 USB 麥克風，耳機只負責聽。

## 專案結構

```
ktvrec/
  comapt.py     COM apartment 管理（STA 給對話框、MTA 給音訊）
  devices.py    裝置列舉與解析
  recorder.py   擷取核心（大緩衝 + 獨立寫檔執行緒）
  mixer.py      對齊、飄移修正、混音
  take.py       錄好但尚未存檔的一段錄音（含增益與時間微調的重混）
  player.py     試聽播放器（播放／暫停／定位）
  waveform.py   波形圖與拖曳定位
  encode.py     ffmpeg 轉檔
  config.py     設定持久化
  gui.py        tkinter 介面
  cli.py        命令列介面
```

播放器每次餵給 WASAPI 的資料量**必須不小於緩衝區**。soundcard 的 `_Player.play()`
在資料比緩衝區空位短時，仍然會向 WASAPI 宣告整個空位都有效，沒填到的部分會把
緩衝區裡的殘留內容當成音訊播出去，播放速率也會掉到即時的八成左右（實測 0.81x）。
`player.py` 因此固定餵滿一個緩衝區，最後不足的一塊補零，修正後為 1.02x。
